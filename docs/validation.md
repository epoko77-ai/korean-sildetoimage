# 검증 범위와 보완 항목

이 문서는 초기 제작, 2026-09-30의 생성 비교·복구 파일럿, 획 복구 도구의 검증 범위를 정리합니다. 각 실험의 입력·평가 단계가 다르므로 결과를 합산하지 않습니다. 시각 판정은 Codex 에이전트의 관측이며, 독립된 사람의 검수나 한글 이미지 생성의 일반적인 성능 벤치마크가 아닙니다.

집계 값은 [검증 결과 JSON](validation-results.json)에도 제공합니다. [대표 전후 비교와 놓침·보류 예시](evidence/README.md)는 약 2MB로 구성했습니다. 전체 실험 이미지·OCR·세부 로그는 로컬 검증용으로 보관합니다.

## 초기 제작 실험

| 항목 | 수행한 검증 |
|---|---|
| 초기 보조 코드 | 단위 테스트 32개 통과 |
| 사전 프롬프트 비교 | 같은 슬라이드 원문·디자인으로 기존 프롬프트와 문구 분리 프롬프트를 각각 2회 실행 |
| 생성형 수정 | 같은 오자 이미지에 부분 수정 요청 1회 |
| 로컬 폰트 복구 | 같은 단어에 두 굵기의 폰트를 적용해 비교 |
| OCR | Apple Vision, 언어 교정 비활성화, 실제 PNG 8개 |
| 최종 후보 | 원문 14개 시각 대조, 디자인 확인, 지정 영역 밖 변경 0픽셀 |

프롬프트 비교의 네 생성본에는 각각 적어도 한 곳의 확인된 한글 오류가 남았습니다. 생성형 수정도 목표 글자의 획을 완전히 복구하지 못했습니다. 해당 사례의 최종 후보는 폰트 기반 렌더링과 국소 합성으로 만들었습니다. 이 결과로 문구 분리가 무용하다거나 폰트 복구가 모든 배경에서 성공한다고 결론 내릴 수는 없습니다.

시각 검수자는 작업을 수행한 Codex 에이전트였습니다. 독립된 사람의 검수 결과가 아닙니다. 실패한 생성본은 핵심 오류 확인 후 제외했고 모든 글자를 정상 또는 오류로 분류하지는 않았습니다. 한 단어의 최초 축소본 판독을 확대 확인 뒤 정정한 사례도 있습니다.

단위 테스트는 실제 한글 획을 판독하지 않습니다. 인위적인 이미지와 검수 기록으로 프로그램이 파일·판정·픽셀 보존 조건을 올바르게 처리하는지 확인합니다.

## 생성 전 지침 비교: 48장

8개 원문·디자인 조건마다 스킬 사전 지침 사용·미사용을 각각 3회 실행했습니다. 각 군은 24장, 원문 항목 465개, 기대 한글 6,678자입니다. 최초 생성본을 평가했으며, 오류 수정이나 성공할 때까지 재생성을 하지 않았습니다.

| 항목 | 사전 지침 없음 | 사전 지침 사용 |
|---|---:|---:|
| 한글 문구 통과 이미지 | 14/24 | 18/24 |
| 확인된 한글 오류 항목 | 13 | 10 |
| 한글 판독 불확실 항목 | 5 | 5 |
| 숫자 오류 항목 | 1 | 0 |
| 디자인 통과 이미지 | 20/24 | 21/24 |
| 문구·디자인 동시 통과 | 13/24 | 16/24 |

작은 본문 조건의 한글 통과는 양쪽 모두 0/3장이었고, 오류 항목은 지침 미사용 4개·사용 6개였습니다. 각주 조건은 요청한 글자 높이 15–17픽셀 대신 실제 약 19–23픽셀로 생성되어, 목표 크기에서의 성능 검증으로 볼 수 없습니다. 판독 불확실 항목이 있어 전체 문자 오류율(CER)은 산출하지 않았습니다.

이 결과는 편의적으로 고른 8개 스트레스 조건의 기술 통계입니다. 스킬 전체의 효과나 안정적인 향상률을 증명하지 않습니다. 검수·수정 기능은 이 생성 비교에 포함되지 않았습니다.

## 알려진 오류의 복구 파일럿: 7곳 × 3방법

6개 기준 이미지의 7개 알려진 오류 위치에 세 방법을 적용했습니다. A는 단어 생성형 수정, B는 정답 글자 모양 참조를 넣은 한 글자 생성형 수정, C는 원본을 보고 미리 정한 픽셀의 획 복구입니다. A/B 결과도 고정한 영역 안에만 합성했습니다. 각 후보는 방법을 모르는 AI 검수자 2명이 판독했습니다.

| 항목 | A: 단어 생성형 | B: 글자 참조 생성형 | C: 수동 획 복구 |
|---|---:|---:|---:|
| 목표 문구 정확 | 3/7 | 2/7 | 5/7 |
| 목표 문구 오류 | 2/7 | 4/7 | 1/7 |
| 목표 문구 불확실 | 2/7 | 1/7 | 1/7 |
| 디자인 통과 | 7/7 | 7/7 | 7/7 |
| 문구·디자인 동시 통과 | 3/7 | 2/7 | 5/7 |
| OCR에 정답 단어가 나타남 | 3/7 | 2/7 | 7/7 |

C는 후보당 6–16픽셀, 합계 71픽셀을 바꿨고 실제 획 마스크 밖 변경은 0이었습니다. 그런데 OCR은 C의 7개 모두에서 정답 단어를 보고했지만 시각 검수는 5개만 통과했습니다. 아래 돌출을 지운 뒤 위 돌출이 남아 `증` 대신 `종`으로 읽힌 사례와, 받침 `ㅁ`에 줄을 넣어도 올바른 `ㅂ` 구조가 되지 않은 사례가 있었습니다. **자모 차이와 OCR 일치만으로 복구 완료를 판단할 수 없습니다.**

원본부터 두 검수자가 오류라고 합의한 것은 3곳이고, 나머지 4곳은 원본 판독이 불확실했습니다. 확정 오류 3곳만 보면 동시 통과는 A 2/3, B 1/3, C 3/3입니다. 전체 5/7을 모두 확정 오류의 개선으로 세면 안 됩니다. A와 B는 편집 단위도 달라 참조 이미지의 효과만 분리한 실험이 아닙니다.

C의 관측된 공동 준비 시간은 약 568초, 적용 시간은 0.83초였습니다. 준비 시간에는 좌표·획 선택과 검사 코드 작성 등이 포함되며 최초 자료 읽기는 빠져 있어 전체 시간의 하한입니다. A/B의 각 7회 생성 호출 시간은 약 323초/319초이며 준비·검수는 제외합니다. 이 서로 다른 시간을 직접 비교해 속도 우위를 주장하지 않습니다.

주변 정상 문구 10개는 세 방법 모두 보존했습니다. 이미 오류 위치를 준 시험이므로 정상 입력의 오수정률이나 오류 위치 탐지 성능을 검증한 것은 아닙니다.

## 재사용 가능한 획 복구 도구

파일럿 결과를 바탕으로 `stroke_repair.py`와 `workflow.py --kind local-stroke`를 추가했습니다. 지원 범위는 초성·종성이 같고 중성만 `ㅗ/ㅜ→ㅡ` 또는 `ㅕ→ㅓ`로 다른, 시각적으로 확인한 한 음절 오류입니다. 실행자가 원문과 실제 글자를 대조하고 위치와 작은 연결 마스크를 정합니다. OCR은 위치 힌트만 제공하며 정상·불확실 글자는 수정하지 않습니다.

획 복구 도구 도입 시 기계 테스트 44개가 통과했습니다. 추가한 12개는 정상·불확실·미지원 입력 거절, 원문·마스크 연결, 잘못된 보간 이웃, 고정 전 적용 거절, 실제 획 마스크 안팎의 변경, `gate/release`의 재검사, 비어 있거나 잘못된 OCR 좌표의 시각 검수 전환을 확인합니다. 별도 코드 검수의 19개 assertion도 통과했습니다. 이후 글자 분리 점검 8개와 2026-10-07의 검수·원본 연결 및 위치 지정 테스트 21개를 더해 현재 73개입니다. 이 수치는 실제 글자 판독 정확도가 아닙니다.

획 복구는 지정된 픽셀의 선형 보간입니다. 자동 획 분할, 일반 배경 복원, 임의 한글 교정 모델이 아닙니다. 같은 중성 차이라도 서체의 획 위치가 다르거나 배경·그림자가 복잡하면 보류해야 합니다.

## 위치를 숨긴 별도 시험: 통제 카드 18장

복구 코드를 보지 않은 별도 에이전트가 정상 8장, 단순 모음 오류 8장, 복잡한 배경·겹받침 변경 2장을 제작했습니다. 이전 파일럿의 단어를 재사용하지 않았으며, Apple SD Gothic Neo·NanumGothic·NanumMyeongjo의 22–42픽셀 글자를 사용했습니다. **실제 AI 생성 이미지가 아니라 폰트로 렌더링한 통제 자료입니다.**

실행자 2명에게는 원문과 이미지뿐인 9장씩을 주었습니다. 오류 여부·정답 좌표·폰트·깨끗한 정답 이미지는 공개하지 않았습니다. 구현 파일을 먼저 고정하고, 카드당 적용 후보 1개만 허용했습니다. 최종 결과를 해시로 고정한 뒤 정답표를 열었습니다. 실행자 판정을 보지 않은 별도 AI가 전체·확대를 검수했고, 이후 정답 음절 참조로 실제 획도 재확인했습니다.

| 항목 | 결과 |
|---|---:|
| 입력 | 오류 10장 + 정상 8장 |
| 실행자가 발견한 오류 | 9/10 |
| 실행자가 정상으로 잘못 판단한 오류 | 1/10 |
| 수정 시도·문구와 디자인 통과 | 7장·7장 |
| 복구 범위 밖으로 보류 | 2장 |
| 정상 이미지 오수정 | 0/8 |
| 선택한 획 마스크가 실제 오자 영역 안에 있음 | 7/7 |
| 실제 획 마스크 밖 변경 | 모든 수정에서 0픽셀 |

수정량은 각 44·28·6·36·9·30·14픽셀, 합계 167픽셀이었습니다. 단순 모음 오류 8장 중 7장을 고쳤으며, 전체 오류 10장 중 최종적으로 3장이 남았습니다. 성공한 시도만 분모로 삼은 7/7을 전체 오류 해결률로 제시하지 않습니다.

놓친 것은 `뎌→더`입니다. 원시 OCR·실행자·별도 AI 검수자가 모두 `더`로 읽었습니다. 정답표 공개 뒤 음절만 8배로 확인하면 `ㅕ`의 가로팔 두 개가 보입니다. 최초 판정을 덮어쓰거나 추가 수정을 해서 시험 성적을 높이지 않았습니다. **검수 기록이 모두 갖춰져도 판독 오류가 남을 수 있다는 직접적인 한계입니다.** 겹받침 보류 사례는 별도 검수에서도 판독이 불확실했으며, 남은 오류 수에는 고정된 폰트 렌더 원문을 기준으로 포함했습니다.

정답 폰트 렌더와 수정 결과는 픽셀 단위로 같지 않습니다. 다른 자모의 위치·너비까지 다시 조판하지 않았으며, 이 시험의 통과 기준은 글자가 올바르게 읽히고 주변 디자인이 유지되는지입니다. 같은 폰트의 정확한 원형 복원을 입증한 결과가 아닙니다.

실행자의 OCR 환경에서는 오류가 발생해 주 에이전트가 같은 입력·고정된 Swift 스크립트로 실제 OCR을 대행했습니다. 정답이나 좌표를 추가로 알려주지는 않았습니다. 권한 대기·중단이 경과시간에 포함되어 능동 처리시간이나 속도 우위는 산출하지 않았습니다.

결과 고정 후에는 별도의 재현 실험에서 발견한 OCR 좌표 예외를 수정했습니다. 공백의 `[0,0,0,0]` 같은 좌표 때문에 전체 위치 찾기가 멈추던 경우를, 문자 차이는 보존하고 위치는 시각 확인으로 넘기도록 바꿨습니다. 회귀 테스트를 추가했으며, 이를 위 18장의 오류 탐지 성능 개선으로 계산하지 않았습니다.

## 새 생성 슬라이드 2장: 별도 확인

오자를 의도적으로 넣은 프롬프트로 이미지 2장을 새로 생성하고, 생성 프롬프트나 오류 위치를 모르는 실행자에게 이미지와 올바른 원문을 주었습니다. 재생성은 없었으며 각 이미지당 획 수정 후보는 최대 1개였습니다. 자연 발생 오류의 표본이나 위 18장의 일부가 아닙니다.

- 밝은 배경의 `군거→근거`: 199픽셀 수정, 마스크 밖 변경 0, 전체 문구·디자인 및 출고 검사 통과.
- 사진 배경의 `셔류→서류`: 보류. 두 팔 중 어느 하나를 지워도 주변 정상 `서`의 가로획 높이와 맞지 않았습니다. 원문에 없는 날짜·서랍 라벨·책 인쇄도 남아 원본을 유지했습니다.

두 번째 사례는 같은 `ㅕ→ㅓ` 자모 차이라도 실제 획 배치가 단순 삭제에 적합하지 않을 수 있음을 보여 줍니다. 첫 번째 사례의 성공을 모든 사진·서체·작은 글씨에 일반화할 수 없습니다.

## 글자 분리 점검 비교: 12장 + 추가 36장

이 시험은 **생성 정확도나 획 삭제 성공률이 아니라 오류 탐지**를 비교합니다. `glyph_inspect.py`는 OCR이 일치한 `ㅡ`·`ㅓ` 음절과 개별 대응 가능한 OCR 불일치도 확대합니다. 위치 힌트가 실제 획에서 어긋날 수 있어 여백을 포함하며, 정답 목록과 판독 카드를 분리합니다. 보이는 음절을 먼저 전사한 뒤 원문과 전체 문맥에서 다시 확인합니다.

별도 에이전트가 처음 12장, 추가로 36장을 제작했습니다. 각 표본은 오류·정상 입력을 절반씩 포함하며, 초성·종성은 같고 중성만 바뀐 실제 유니코드 글자를 같은 폰트로 렌더링했습니다. 오류는 `ㅗ→ㅡ`, `ㅜ→ㅡ`, `ㅕ→ㅓ`를 균등하게 배치했습니다. Apple SD Gothic Neo·NanumGothic·NanumMyeongjo, 밝고 어두운 배경을 사용했고, 추가 36장은 18·22·26·30·36·42픽셀 크기를 각 6장씩 포함합니다.

기존 검수와 새 점검은 표본별로 서로 다른 새 에이전트가 수행했습니다. 기존 검수는 원문·전체 이미지·원시 OCR을 보고 필요에 따라 확대했습니다. 새 방식은 정답 없이 글자 카드를 먼저 읽어 봉인한 뒤 원문·전체 문맥을 확인했습니다. 오자 여부·위치·글꼴·정답 이미지는 검수자에게 숨겼고, 결과를 고정한 다음 정답표를 열었습니다. 추가 시험에서도 코드는 바꾸지 않았습니다.

| 표본 | 실제 오류 | 기존 검수 발견 | 분리 점검 + 문맥 확인 | 정상 입력 오판, 기존 / 새 방식 |
|---|---:|---:|---:|---:|
| 첫 12장 | 6 | 5 | 6 | 0/6 · 0/6 |
| 추가 36장 | 18 | 17 | 18 | 0/18 · 0/18 |
| 합계 48장 | 24 | 22 | 24 | 0/24 · 0/24 |

첫 시험의 `꿑→끝`, 추가 시험의 `뗙→떡`을 기존 검수가 놓쳤고 새 방식이 발견했습니다. 후자는 42픽셀의 큰 글씨였습니다. 작은 글씨뿐 아니라 문맥에 맞게 보완해 읽는 문제도 남아 있음을 보여 주는 사례입니다.

**글자 카드만의 판독은 완벽하지 않았습니다.** 전체 145개 카드 중 143개를 실제 글자와 같게 전사했고 1개는 오독, 1개는 불확실했습니다. 카드 단계에서 확정 차이로 드러난 오류는 22개이며, 전체 문맥 재확인을 포함한 최종 검수에서 24개를 찾았습니다. 따라서 카드를 읽은 결과를 바로 삭제 마스크나 출고 허가로 쓰지 않습니다.

48장은 폰트 통제 자료이며 자연 발생 생성 오류의 대표 표본이 아닙니다. 경로별 검수자가 달라 방식의 효과와 검수자 차이를 분리하지 못합니다. 표본에서 관측한 22→24를 일반적인 향상률이나 무오류 보장으로 해석하지 않습니다. [장별 판정 CSV](inspection-results.csv)와 [전체 집계 JSON](validation-results.json)을 제공합니다.

CSV의 `baseline_status`와 `inspection_status`는 각 검수자가 이미지의 문구를 정상(`correct`) 또는 오류(`incorrect`)로 판정한 값입니다. 실제 오류를 찾았는지는 별도의 `*_error_detected` 열로 표시합니다.

별도 개발 예시로, 첫 시험 채점과 정답 공개가 끝난 뒤 `꿑→끝`을 12픽셀 수정했습니다. 마스크 밖 변경 0, 이미지 생성 호출 0이며 전체·확대 검수, 별도 AI 검수, 실제 OCR과 출고 검사를 통과했습니다. 이 예시는 위 탐지 성적이나 별도 복구 성공률에 합산하지 않습니다.

## 사용성과 디자인 보존 지침 수정

사용 예시는 제작 또는 오타 교정 한 문장으로 줄였습니다. 원문·숫자 보존, 생성 전 문구·배치 검토, 검수와 확인된 오타의 국소 수정은 스킬의 기본 작업으로 명시했습니다.

기존 폰트 비교에서도 같은 문자열의 굵기·자폭이 주변 문구와 달라질 수 있었습니다. 이에 수정 전 기준본의 타이포를 확인하고, 후보를 같은 배율의 확대 영역과 실제 표시 크기에서 비교하도록 지침을 구체화했습니다. 문구와 디자인을 모두 통과한 후보만 채택하며, 재시도 실패 뒤 일반 폰트로 자동 대체하는 경로는 제외했습니다.

폰트 재렌더링은 실제 폰트·조판·효과와 깨끗한 배경을 확보해 현재 타이포를 재현할 수 있는 경우에 검토합니다. 비슷한 폰트로 교체하는 것은 별도의 디자인 변경입니다. 초기 파일럿의 폰트 성공 사례가 모든 이미지에서 원래 타이포를 유지한다는 증거는 아닙니다.

사용 예시를 줄인 것 자체의 효과를 따로 측정한 실험은 없습니다. 아래 프로그램 수준의 제약도 남아 있습니다.

## 확인된 제약

### 여러 단계의 누적 보존: 2026-10-07 보완

이전 `gate`와 `release`의 보존 범위는 해당 요청에 연결된 기준본과 수정 영역이었고, 최초 원본에서 최종본까지의 전체 수정 이력은 자동으로 요구하지 않았습니다.

별도 재현 실험에서 첫 수정과 다음 수정 사이에 허용 영역 밖 1픽셀을 바꿨습니다. 마지막 단계의 `gate`와 `release`는 통과했습니다. 최초 원본과 비교하면 1픽셀 차이가 남았고, 별도 `patch_image.py verify`는 보고서 연결 불일치로 거절했습니다.

새 합성 요청은 `init-run`으로 원본을 고정하고 이전 보고서를 요청에 연결합니다. 원본에서 다음 기준본까지 연결이 끊기면 요청 단계에서 거절하고, `gate/release`에서 중간 이미지와 전체 이력을 다시 검사합니다. 위 1픽셀 사례·보고서 누락·순서 변경·출고 직전 기록 변경은 거절되며 정상 2단계는 통과합니다. 획 복구 단계는 실제 획 마스크도 확인합니다. 과거 schema-1 요청은 `single_step_legacy`로 명시하며 누적 보존을 주장하지 않습니다. ### 선택한 글자 검수의 연결과 실제 문단 위치

이전에는 불확실 판독 2건이 있는 글자 점검과 별도의 긍정적인 전체 검수 기록이 함께 있어도 최종 저장이 가능했습니다. 새 후보 등록은 선택한 packet을 고정하고, `gate/release`가 판독을 다시 대조합니다. 불일치·누락·불확실·위치 미지정 각각의 문맥 재확인 기록이 없으면 `needs_review`로 남습니다. 글자 점검을 선택하지 않은 직접 시각 검수 경로는 유지합니다. 기계 검사는 기록 연결을 확인하며 실제로 읽었는지를 보증하지 않습니다.

이전 생성 비교에서 오류가 확인된 15장·23개 문구에 현재 원시 OCR과 위치 찾기를 적용했습니다. 23개 치환 중 좌표 힌트가 나온 곳은 10곳, 지원 자모 차이 18곳 중 힌트가 나온 곳은 9곳이었습니다. 긴 문단의 오류 7곳에는 힌트가 없었습니다. 이미 검수한 편의 표본의 개발 진단이며, 힌트의 실제 글자 포함 여부를 모두 시각 검증한 수치나 새로운 탐지 정확도·복구 가능 비율은 아닙니다.

실행자가 실제 위치를 확인해 이미지·원문·문구 id·글자 index와 묶는 `--manual-boxes`를 추가했습니다. OCR 없이 선택한 글자만 카드로 만들 수도 있습니다. 위치 상자는 삭제 마스크가 아닙니다. 그 경로로 긴 문단의 알려진 `중가→증가` 사례 한 곳을 9픽셀 수정하고, 최종 카드·전체 화면·실제 OCR·원본 보존 검사까지 통과했습니다. 단일 실행자의 개발 사례이며 기존 성적에 합산하지 않습니다. [비교 그림](evidence/README.md#6-여러-줄-문단-중가--증가)

### 문구 포함 검사

원문이 제목 ‘일자리’, 본문 ‘지역 일자리 확대’인 경우, 본문만 들어간 프롬프트도 부분 문자열 검사에 통과할 수 있습니다. 현재 검사는 각 id에 별도의 표시 문구와 위치가 지정됐는지까지 확인하지 않습니다. 반복되는 같은 문구도 실행자가 위치와 개수를 검토해야 합니다.

### 복구 범위와 실행자의 판단

초기 실험의 폰트 복구 코드는 특정 단어·좌표·폰트와 작은 어두운 배경에 맞춘 코드였습니다. 설치 스킬에 그 사례용 배경 복구 코드는 포함하지 않습니다. 새 획 복구 도구도 자동으로 오류와 마스크를 발견하지는 않습니다. 다른 이미지에서는 배경과 획 구조·기준선·굵기를 실행자가 다시 판단해야 합니다. 픽셀 보존 검사는 올바른 글자나 자연스러운 디자인을 보장하지 않습니다.
